A Linux builder for Nix on your Mac.

HexBox is a nix-darwin module that adds an aarch64-linux remote builder, running in an Apple container machine. It starts when a build needs it and powers off when it goes idle.

inputs.hexbox.url = "github:RobertDeRose/nix-hex-box";

For nix-darwin on Apple silicon. Bring your own container from Homebrew, mise, or Apple’s installer.

A Linux builder that stays out of your way.

Enable one module and Nix on your Mac can build aarch64-linux derivations. HexBox handles the machine, SSH, keys, and recovery, so the builder feels like part of Nix.

One option to turn it on

HexBox sets up nix.buildMachines, SSH aliases, host keys, and a persistent builder machine. Linux derivations go to it automatically.

services.container-builder = {
  enable = true;
};

Starts when a build needs it

An SSH ProxyCommand boots the machine on demand and relays straight to the guest’s sshd, so a changing machine IP never breaks Nix.

nix build .#packages.aarch64-linux.default

Powers off when it’s idle

With no SSH connections for five minutes, the guest shuts down. Its /nix store survives, so the next build reuses what it already has.

idleShutdown.timeoutSeconds = 300;
Your container, your choice
Install Apple’s container with Homebrew, mise, or Apple’s pkg. HexBox finds it on PATH, including from the root nix-daemon.
A small, current builder image
The default image is Alpine with OpenSSH, sudo, and Lix, rebuilt weekly so security updates reach new machines. Pin a versioned tag if you prefer.
Or build your own image
Point imageContainerfile at a Containerfile and HexBox builds a local image and uses it instead.
Verified SSH, not trust-on-first-use
HexBox generates the builder’s host key and a matching known_hosts, so every connection is checked.
host.container.internal for your containers
By default, Apple containers can reach services on your Mac at host.container.internal.
A helper for when things go wrong
The hb command shows status, repairs the runtime and machine, tails logs, and runs a real remote build to prove it works.

How a build runs

Nothing new to learn: Nix uses an ordinary ssh-ng remote builder. HexBox makes the far end of that SSH connection a machine that is always ready to boot.

  1. Nix sees an aarch64-linux derivation and picks the container-builder remote builder.
  2. The root nix-daemon opens SSH, whose ProxyCommand switches to your user, who owns the container runtime.
  3. The proxy starts the nix-builder machine if it isn’t running and waits for a real SSH handshake.
  4. It relays the connection with socat to sshd inside the machine.
  5. Nix logs in as builder and runs the remote nix-daemon through a narrow sudo rule.
  6. The build runs in the guest, and its outputs are copied back to your Mac’s store.
  7. After the idle timeout with no SSH sessions, the guest powers itself off.

Is HexBox for you?

Use HexBox if

  • You manage your Mac with nix-darwin and need to build aarch64-linux derivations.
  • You already use, or want to use, Apple’s container.
  • You want a builder that costs nothing while you aren’t building.
  • You want build results that survive restarts without a remote server.

Look elsewhere if

  • You need x86_64-linux builds; the guest is always aarch64-linux.
  • You’re on an Intel Mac, or don’t use nix-darwin.
  • You need NixOS VM tests at speed: Macs before M3 lack nested virtualization, so they run under emulation.

Install

Three steps: install Apple’s container, add HexBox to your nix-darwin flake, then switch.

1 Install container

Homebrew

brew install container
container system start

mise

Install it globally. The root nix-daemon can’t see a per-project mise install, so for one of those set containerBinary to the path mise which container prints.

mise use -g container
container system start

Apple’s installer

Apple’s signed package installs under /usr/local, so the installer asks for your password.

gh release download --repo apple/container --pattern 'container-*-installer-signed.pkg'
sudo installer -pkg container-*-installer-signed.pkg -target /
container system start

2 Add the module

{
  inputs.hexbox.url = "github:RobertDeRose/nix-hex-box";

  outputs = inputs: {
    darwinConfigurations.my-host = inputs.darwin.lib.darwinSystem {
      system = "aarch64-darwin";
      modules = [
        inputs.hexbox.darwinModules.default
        {
          services.container-builder = {
            enable = true;
            cpus = 4;
            memory = "8G";
          };
        }
      ];
    };
  };
}

3 Switch and test

sudo darwin-rebuild switch --flake .#my-host
hb builder test

The first build pulls the builder image and creates the machine, so it takes longer. After that, the machine boots in seconds when a build needs it.

Good to know before you start
  • The guest is aarch64-linux only.
  • The builder machine defaults to 4 CPUs and 1 GB of memory. Raise memory for anything heavier than small packages.
  • hb builder reset recreates the machine, which deletes the guest’s /nix store. Changing the image does the same.
  • Custom images must provide socat, base64, getent, and a working /sbin/init.
  • Setting a removed option, such as installer.* or socktainer.*, fails evaluation with a message saying what to do.

Check on it with hb

HexBox installs a small helper. Most of the time you never need it; when something breaks, it tells you what and how to fix it.

$ hb builder status
🔨 Builder status
container system   ✅ running
builder machine    ✅ running
ssh handshake      ✅ ready
remote store       ✅ reachable
hb builder status
Runtime, machine, SSH, and remote store at a glance.
hb builder repair
Restarts the runtime, recreates or updates the machine, and checks SSH and networking.
hb builder test
Runs a real remote build to prove the whole path works.
hb builder logs boot
Boot, readiness, and idle-shutdown logs.
hb doctor
Diagnoses the runtime, DNS, and host setup.
